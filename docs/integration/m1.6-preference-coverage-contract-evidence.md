# Milestone 1.6: `preferenceCoverage` and `textCoverage` Contract-Revision Approval and Notification Record

This artifact records the integration-owner approval and the
parallel-stream notification determination for the shared-contract
revisions that introduce the optional `preferenceCoverage` and
`textCoverage` response fields on `feat/m1.6-rank-preferences-group-matching`.
It is the durable evidence required by `AGENTS.md:127` and the integration
rules in `docs/plans/milestone-1-talent-search.md:381-386`, and it closes
the gap the Codex review on commit `b67231a` flagged in `P1-002` against
`docs/contracts/search-api.md:319`.

## Why this file exists

Codex review feedback on commit `b67231a` (P1-002) flagged that the
`## Contract revisions` narrative at `docs/contracts/search-api.md:319`
explained the proposed `preferenceCoverage` field but recorded no
approver, approval decision/reference, date, or stream notification
recipients/status. It also flagged that the prior draft of this artifact
claimed an earlier commit as the approval commit while actually being
authored in `b67231a`, and made a sole-committer claim contradicted by
the branch history. That evidence is captured here against the actual
authoring commit, with provenance reconciled against `git log`.

## Exact shared-contract surface changed

The M1.6 branch (`feat/m1.6-rank-preferences-group-matching`) extends
the existing v1 contract with two optional response fields. The change
is named with the file and the conceptual purpose so the
integration-owner approval is auditable:

| Surface         | File                                         | Purpose                                                                                                                                                                                                                                                                                                                                                                                                  |
| --------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shared types    | `packages/types/src/index.ts`                | Adds the public `preferenceCoverageV1Schema` and `textCoverageV1Schema` plus the inferred `PreferenceCoverageV1` and `TextCoverageV1` types, and wires both into `talentSearchResultV1Schema` as optional fields. The schemas enforce `matched <= total`, are independent of `relevanceScore`, and are shared with the browser and the API so neither side holds a parallel handwritten DTO.             |
| Public contract | `docs/contracts/search-api.md`               | Documents both optional response fields on `TalentSearchResultV1`, records the omission semantics (`preferenceCoverage` is emitted whenever the buyer supplied at least one canonical preference atom; `textCoverage` is emitted whenever the buyer supplied at least one canonical query token; neither is emitted as a "0 of 0" payload), and pins the `## Contract revisions` entry to this evidence. |
| Specification   | `docs/specs/milestone-1-talent-search.md`    | Adds the buyer-facing coverage statements to the Implementation Decisions list and names the omission semantics so the service, the runtime schema, the public contract, and the specification describe the same behavior.                                                                                                                                                                               |
| Buyer UI        | `apps/web/src/app/components/SearchPage.tsx` | Renders both coverage lines (one per emitted field) as factual non-percentage qualitative-fit blocks distinct from `matchReason`, alongside the unchanged `Why this matches` evidence block.                                                                                                                                                                                                             |
